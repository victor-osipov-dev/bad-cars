# Архитектура RoadRage

Версия 0.2 (этап 2). Документ описывает целевое устройство и уже зафиксированные
решения.

## 1. Слои

```
src/
  core/        чистые утилиты: время, фиксированный шаг, математика, RNG
  data/        типизированные конфигурации (машины, оружие, здания, рейды...)
  sim/         детерминированная симуляция, без DOM и Babylon.js
  render/      интеграция Babylon.js: сцена, камера, спрайты, интерполяция
  ui/          HTML/CSS-интерфейс, HUD, экранные контролы
  app/         композиция: связывает sim + render + ui + ввод
  platform/    IndexedDB, настройки, миграции сохранений (позже)
```

Правило зависимостей: `app → (render, ui, sim, platform)`, `sim → (core, data)`,
`render → (core, data, snapshot-типы sim)`, `ui` не зависит от sim/render,
`core` ни от чего не зависит. Рендер импортирует из `sim` только типы снапшота
(без runtime-кода), симуляция из render/ui не импортирует ничего.

## 2. Симуляция и рендер

- `Simulation` владеет `WorldState`, `GameTime`, `SeededRandom` и списком систем.
- `Simulation.step()` вызывается только с фиксированным шагом и не знает о
  реальном времени, FPS, DOM и GPU.
- Рендер получает `WorldSnapshot` — сериализуемое представление состояния.
  Рендер не мутирует состояние симуляции.
- Позиции спрайтов берутся из снапшота; для плавности рендер интерполирует
  предыдущий и текущий снапшоты по `alpha` из драйвера (позиция, курс, руль,
  скорость). Камера сглаживается по реальному времени кадра и не влияет на
  симуляцию.

## 3. Фиксированный шаг

- Шаг: `1/60` с (`GAME_CONFIG.fixedStepHz = 60`).
- `FixedStepDriver` накапливает реальное время, ограничивает кадр
  (`maxFrameDeltaSeconds = 0.25`) и число подшагов (`maxSubSteps = 8`).
  Драйвер только планирует тики: время и мир двигает `Simulation.step()`,
  вызываемый из колбэка ровно один раз на тик.
- Излишек времени при перегрузке отбрасывается и учитывается в
  `droppedSeconds`, чтобы избежать «спирали смерти».
- `GameTime` хранит номер тика и вычисляет время как `tick * step`, что
  исключает накопление ошибки. Игровые сутки — настраиваемая длительность.
- Пауза останавливает вызовы `Simulation.step()`, но рендер продолжается.

## 4. Детерминизм и RNG

- Вся случайность в симуляции — через `SeededRandom` (mulberry32).
- RNG имеет состояние (`state`), пригодное для сохранения/восстановления.
- Системы не читают системное время. Все решения принимаются по тику и
  входным командам.

## 5. Системы и состояние

- `System` — объект с `id` и `update(ctx, dt)`, выполняется в
  зарегистрированном порядке.
- Ввод передаётся командами `DriveCommand` с номером тика. `CommandQueue`
  применяет команды по порядку, последняя команда остаётся активной; прямых
  мутаций состояния из UI нет. Это основа детерминированного реплея и будущего
  сетевого слоя.
- Боковой базис выводится из продольного вектора (`rightOf`), а не вторым
  `fromAngle`: так оси остаются строго ортогональными и боковая скорость не
  «протекает» обратно в продольную на кардинальных углах.
- Модель машины аркадная: скорость раскладывается на продольную и поперечную
  составляющие; авто-газ ускоряет до предела, сопротивление и тормоз гасят
  продольную скорость, сцепление гасит поперечную (ручник снижает сцепление),
  руль плавно приближается к целевому положению, а угловая скорость зависит от
  скорости и падает на высоких скоростях. Твёрдые объекты и границы арены
  разрешаются круговыми коллизиями с восстановлением и потерей энергии.
- Состояние мира — простые сериализуемые структуры (числа, массивы, объекты),
  без ссылок на Babylon-объекты.
- Сущности получают стабильные числовые/строковые ID. Для чанков и баз ID
  детерминированы от координат/индекса.
- Позже: пространственный индекс (сетка) для поиска целей и коллизий.

Порядок систем фиксирован (детерминизм): `vehicle-movement` → `weapons` →
`projectiles` → `enemies` → `vehicle-durability` → `effects`.

| Система | Ответственность |
| --- | --- |
| `vehicle-movement` | инерция, поворот, автодвижение, задний ход, коллизии с ареной и объектами |
| `weapons` | прицел башни, слоты, патроны, перезарядка, выстрел игрока |
| `projectiles` | баллистика, swept-коллизии, урон по фракциям |
| `enemies` | наведение турелей, огонь по игроку, респавн целей |
| `vehicle-durability` | разрушение машины и восстановление на спавне |
| `effects` | время жизни визуальных эффектов |
| `world/chunks` | стриминг чанков, ресурсные узлы, площадки |
| `resources` | добыча, багажник, разгрузка |
| `bases` | строительство, склад, состояние сооружений |
| `economy` | содержание, цены, производство |
| `enemies` | спавн, ИИ, патрули, атаки |
| `defense` | турели, мины, ловушки, датчики |
| `raids` | планирование, живой бой, грабёж, захват |
| `remote-sim` | офлайн/удалённое разрешение событий |
| `progression` | гараж, слоты, улучшения |

## 5a. Экономика и добыча

- Ресурсы — данные (`src/data/resources.ts`): три вида, сложность добычи,
  размер узла, конфиг инвентаря.
- `EconomyState` живёт в `WorldState`: `cargo`, `storage`, `cargoCapacity`,
  дробные аккумуляторы добычи/разгрузки и `depletion` — карта «id узла →
  остаток».
- Передачи всегда целочисленные и гейтятся аккумулятором
  (`progress += rate·dt`, затем `while progress >= 1`), поэтому скорости
  точны, а суммарное количество ресурсов сохраняется на всех переходах
  узел → багажник → склад.
- `ResourceSystem` выбирает ближайший узел в радиусе
  (`collision.radius + harvestReach`), приоритет у разгрузки: стоя на
  площадке базы с грузом игрок разгружается, иначе добывает.
- Стриминг не должен «возрождать» выработанные узлы: `mergeChunkContent`
  применяет `depletion` при каждой (пере)загрузке чанка.
- Взаимодействие идёт через `interact` в `DriveControls`, то есть тем же
  тик-командным путём, что и вождение — реплей остаётся детерминированным.

## 5b. Базы и строительство

- Площадки (`baseSites`) генерируются вместе с чанком и живут в нём; занятость
  определяется списком баз, а не флагом в чанке, поэтому выгрузка чанка не
  «освобождает» базу.
- `BaseState` хранит позицию, склад и список `StructureState`. Склады
  принадлежат базам: `economy.storage` не существует, разгрузка идёт в склад
  ближайшей базы в радиусе.
- Размещение — фиксированные слоты (`BASE_SLOTS`), поэтому «первый свободный
  слот» детерминирован, а проверка пересечений сводится к занятости слота.
  Порядок проверок: лимит вида → лимит базы → ресурсы → слот.
- Основание и постройка — edge-триггеры: монотонные токены в
  `DriveControls`, системы сравнивают их с последним обработанным значением.
  Удержание клавиши действует один раз, реплей команд воспроизводит застройку.
- Оплата атомарна: `payCost` сначала проверяет всё и только потом списывает,
  так что неудачная постройка не съедает ресурсы частично.

## 5c. Экономика баз

- Ставки заданы на минуту (`STRUCTURE_ECONOMY`), симуляция переводит их в
  посекундные и копит дробные аккумуляторы на сооружение; списание и
  начисление — только целыми единицами, поэтому склад не уходит в минус и
  результат воспроизводим на длинных интервалах.
- Сооружение считается снабжённым, только если на складе есть **целая
  единица** каждого потребляемого ресурса. Иначе оно сразу неактивно: не
  производит и копит `deficitSeconds`. Так база без топлива не держит турель
  в сети «в кредит».
- После `graceSeconds` дефицита сооружение теряет по одному условию за каждые
  `degradationSeconds`; при нуле списывается (`scrappedCount`). Пополнение
  склада возвращает структуру в строй и сбрасывает таймер.
- `baseEconomyRates` даёт нетто/содержание/производство на минуту для HUD и
  снапшота, считая неактивные сооружения в расходе, но не в производстве.

## 6. Мир и чанки

- Мир — квадратная сетка чанков (`WorldConfig.chunkSize`, по умолчанию 24
  мира-единицы), ограниченная прямоугольником `halfWidth × halfHeight`.
- Генерация детерминирована: `generateChunk(coord, seed)` — чистая функция.
  Свой `SeededRandom` на чанк, сид = хеш `(worldSeed, chunkX, chunkY)`;
  порядок генерации не влияет на результат, выгрузка/повторная загрузка дают
  идентичное содержимое. Это же свойство понадобится для сетевой игры.
- Пропсы размещаются по сетке 3×3 внутри чанка и обрезаются по его границам,
  поэтому соседние чанки стыкуются без зазоров и наложений.
- Стриминг: `streamChunks` (чистая функция) грузит чанки в радиусе
  `activeRadiusChunks` и выгружает за `unloadRadiusChunks`. Разные радиусы
  дают гистерезис: чанк на границе не перегенерируется каждый тик.
  `ChunkStreamingSystem` вызывает её только при смене координаты чанка.
- Память ограничена: резидентно не больше `(2·unloadRadius+1)²` чанков,
  рендер освобождает меши выгруженных чанков и пропсов.
- Биомы (`wasteland`, `dunes`, `scrapyard`, `ruins`) задают плотность и
  состав пропсов; узлы ресурсов генерируются заранее для этапа 5.
- Рукописные пропсы стартового полигона всегда резидентны и накладываются
  поверх процедурных; зона вокруг спавна остаётся чистой
  (`spawnClearRadius`).
- Земля рисуется одним бесшовным тайлом с постоянной плотностью пикселей;
  биом дополнительно подкрашивается очень слабой (alpha 0.07) подложкой,
  чтобы не проявлять сетку чанков.

- Активные чанки обновляются
  каждый тик; неактивные замораживаются.
- Генерация детерминирована от `(worldSeed, chunkX, chunkY)`.
- Ресурсные узлы и площадки под базы генерируются в чанке и хранят состояние
  (истощён/занят) до выгрузки.

## 7. Базы и удалённая симуляция

- База: ID, координаты, склад, сооружения, состояние, уровень угрозы.
- Онлайн-рейд (игрок рядом) моделируется в общем мире на 60 Гц.
- Удалённые рейды разрешаются планировщиком `RemoteSimulator`:
  - события планируются на конкретные игровые тики;
  - при пропуске времени выполняется агрегированный расчёт по шагам
    (например, 1 с), а не миллионы 60 Гц тиков;
  - исход детерминирован (RNG берётся из состояния мира);
  - результат — отчёт о рейде + изменения состояния базы.
- Рендер не требуется; тот же код работает в Web Worker/на сервере в будущем.

## 8. Сохранения и версионирование

- IndexedDB (`platform/storage`), один объект на слот.
- Формат:
  ```ts
  interface SaveFile {
    schemaVersion: number;   // SAVE_SCHEMA_VERSION
    savedAt: number;         // реальное время (только метаданные)
    game: SerializedGameState;
  }
  ```
- Миграции — упорядоченный список `migration(fromVersion) → toVersion`.
- При несовместимости — резервная копия и понятное сообщение игроку.
- Автосохранение по таймеру и после значимых событий.

## 9. Мультиплеерная готовность

- Ввод игрока оформляется командами (`Command`) с номером тика, а не прямыми
  мутациями состояния.
- Состояние сериализуемо, симуляция детерминирована.
- Нет глобальных синглтонов; зависимости передаются через контекст.
- Сетевой слой сможет принимать команды и рассылать снапшоты без изменения
  игровых систем.

## 10. Рендер (Babylon.js)

- `Engine` + `Scene`, один ортографический `FreeCamera` строго сверху:
  позиция над плоскостью XY, направление по −Z, `up = +Y`.
- Плоскость мира — XY; координаты симуляции `(x, y)` совпадают с мировыми.
- Pixel art: низкое разрешение рендера (`hardwareScalingLevel`), текстуры
  `NEAREST_SAMPLINGMODE`, без сглаживания, спрайты на плоскостях.
- Сцена right-handed, +X вправо, +Y вверх; камера над +Z смотрит в −Z.
- UV текстур инвертированы по V, чтобы верх canvas совпадал с +Y мира.
- Спрайты генерируются процедурно (`DynamicTexture`) до появления ассетов.
- Камера следует за машиной: dead-zone, экспоненциальное сглаживание,
  ограничение центра вида границами арены, минимальная ширина вида для
  портретных экранов. Z-order задаётся слоями (земля, площадки, ящики, скалы,
  машина).
- HUD — DOM поверх canvas, не часть 3D-сцены.

## 11. Производительность

- Ограниченный шаг и maxSubSteps; пул снарядов/эффектов.
- Стриминг чанков и отсечение по видимой области.
- Удалённые базы не обновляются поштучно каждый кадр — только планировщиком.
- Цель MVP: 60 FPS на десктопе, ≥30 FPS на среднем мобильном.

## 12. Тестирование

- `vitest` (node) — чистая математика, время, системы, экономика, рейды,
  миграции сохранений.
- Сценарные тесты симуляции: одинаковая последовательность команд + seed даёт
  одинаковый снапшот.
- Playwright — загрузка страницы, canvas, пауза, клавиатурное вождение,
  мобильный resize и touch-руль, отсутствие ошибок консоли.
